# Users, roles and access matrix

Read this before changing any procedure, route gate or schema field. The table headings and procedure cells are consumed by `scripts/check-access-matrix.ts`; update them in the same change as the procedure.

## Roles

| Role | Who |
|---|---|
| Anonymous | Not signed in; can view public pages and available authentication flows. |
| User | Owns packages, proposals, SSH keys, known hosts, MCP credentials and conversations. |
| Admin | User rights over their own data, plus user management, instance settings, jobs, backup status and repository storage management. |

Admins cannot read another user's packages, conversations, summary overrides, keys or tokens. They cannot impersonate users, set another user's password or email directly, or list their sessions. Invites provide a one-time set-password link, never a password. The one password path is `users.passwordLink`: an admin can issue a one-time set-password link for a non-admin account that signs in with a password. With SMTP it goes only to the user's mailbox (a failed send revokes it); without SMTP the admin sees it once, so on such a server an admin could use it to set that user's password. Every link is audited, and admin accounts never receive one (demote first, itself a visible action). Only a link mailed to the address verifies it when spent, recorded per link after the mail was accepted. A link the admin was shown (the invite email failed) sets the password and verifies nothing, and with SMTP it works only while the account is still a pending invite: once the invitee verifies their address, links an SSO identity or signs in, the reset endpoint refuses it like an expired link (`isResetLinkRedeemable` in `packages/auth/src/password-reset-links.ts`). Setting a password by any link deletes the user's other links. Role demotion, archive and deletion preserve the last verified active admin through a shared Serializable transaction; role changes require named confirmation and are audited. Better Auth’s parallel role/ban/remove and access-field update endpoints are blocked at the HTTP gate. Admins create accounts only through `users.invite`: Better-Auth's own `/api/auth/admin/create-user` route is refused over HTTP, and no admin route can change an address or mark it verified (the admin role lacks `set-email`); a new account arrives verified only from an SSO sign-in, or on a server without SMTP, where every account is (`refuseUnprovedUserCreation` in `packages/auth/src/user-creation-policy.ts`). Storage administrators can see repository URLs, sizes, last use and private owners, and delete caches. The host/database operator necessarily has infrastructure access; these are application permissions.

## Ownership rules

Queries scope packages, proposals, credentials, conversations, runs and turns to the acting user. Foreign IDs return NOT_FOUND. MCP identity comes from its credential, never a tool argument. API tokens authorize MCP tools only, never browser procedures or admin functions.

A banned user (permanent, or a temporary ban that has not lapsed) has no access: every authenticated procedure refuses the session (`checkSessionAccess` in `packages/api/src/index.ts`, which `checkAdminAuthority` also starts with) with UNAUTHORIZED, or NOT_FOUND on the 404-hidden admin procedures, including a session issued before the ban, and MCP credentials of a banned user are refused. The check reads the session's user as Better-Auth resolves it, so a browser holding a signed session cookie cache from before the ban keeps access for at most its 60 s lifetime (`cookieCache.maxAge` in `packages/auth/src/index.ts`), as it does after a session is deleted. Every supported ban path also deletes the user's sessions (`users.archive` and account removal; the parallel admin-plugin access writes are blocked at the HTTP gate), so that 60 s is the whole window; it is kept deliberately, because closing it would cost an authoritative DB read per request or no cookie cache. Better-Auth's own routes (`/api/auth/*`: profile update, 2FA, OAuth consent and continue, and the rest) refuse a banned user's surviving session with 401, except sign-out, and delete that user's sessions (`bannedSessionGuard`, `packages/auth/src/banned-session-guard.ts`), within the same 60 s bound; a failed session lookup there fails the request instead of passing it. Open live subscriptions (`conversations.watch`, `conversations.activity`) are closed with UNAUTHORIZED when the ban is announced, without delivering anything they had buffered (`packages/api/src/lib/live-streams.ts`), and each new one re-reads the ban state from the database when it opens, so the cookie-cache window does not let a stream in either. A ban written straight to the database announces nothing: it reaches streams that open afterwards, not ones already open. An MCP request in flight (a streamed `query_dependency`, a parked `get_query_result`) is aborted and its response ended when the ban is announced (`createMcpRequestHandler`), and every announced ban stops the user's runs.

Public HTTPS repository clones, checkouts and generated overviews can be shared through each user's own packages. Private SSH repositories are owner-isolated even when URLs match. A user's edited overview is private. MCP proposal and auto-approval flags further restrict each credential; human account, credential and SSH management remain web actions.

## Sensitive boundaries

Before changing the password or consuming a forgot-password or set-password link, a pre-sweep atomically deletes all of the user's sessions and revokes their MCP personal/API tokens and OAuth grants, access tokens, refresh tokens and remembered consent under the credential-issuance lock; after Better Auth commits the reset, a second full session/credential sweep runs as defense in depth. Both sweeps also delete the user’s pending two-factor sign-in challenges, their OTP and attempt-counter rows, and trusted-device verification rows under the same lock. There is no server-side session cache or secondary storage; signed browser cookie copies stop working within their cache window (≤ 60 s), but cannot mint credentials because issuance re-checks the live session under the same lock; session-authenticated Better Auth writes also re-check the database before any cache renewal, clearing session and cache cookies with a 401 for missing or expired sessions. A pre-sweep verification-lookup or revocation failure is logged and returns 503 with the password and reset token intact. The reset alone uses a real adapter transaction: authoritative eligibility, consumption of the token and its mailbox-bound mailed proof, deletion of competing links, email verification and the password write share one client and commit together. A failure rolls these writes back, allowing retry with the same token; the independent pre-sweep remains committed, so old sessions remain revoked while the old password is unchanged. A post-sweep failure is logged and rethrown after the password, mailbox verification and competing-link deletion have committed. A shown link never verifies an address. The existing private mode without SMTP still permits an active password account's admin-issued link; its authoritative admission uses the current email configuration and introduces no new proof kind. This app has no machine enrollment or host/node credential model; its standing MCP API tokens and OAuth grants are included in both sweeps.

An authorized internal IdP account insertion captures pending-invite state before linking. Under the same three locks it clears a pending invite's prior password and revokes old sessions, pending two-factor rows and standing MCP credentials on the insertion transaction. Grant generations remain tombstones; OAuth access, refresh and consent rows are deleted in dependency order. A second committed sweep catches old-password rows inserted before that clearing commit. Session-revocation notification runs in finally after that sweep, closing conversation streams and MCP exchanges admitted during cleanup without banning the user or stopping runs. Account insertion returns only after this cleanup, before Better Auth creates the legitimate IdP session. Failed insertion transactions roll back both linking and cleanup; a final-sweep failure fails linking after the password was cleared and still announces teardown. Verified active accounts keep their existing passwords and credentials, and fresh SSO signup remains supported. The pinned default requires local email verification for ordinary implicit linking, so pending invitations remain denied over the default HTTP SSO path; the protected internal seam grants no new provider trust, linking exemption, session exemption, signup flag or forced-SSO exception.

Successful resets fence in-flight password proof (`packages/auth/src/password-sign-in-fence.ts`). Password sign-in snapshots the credential fingerprint before verification, checks it before insertion, and checks again after the session or 2FA challenge commits. Two-factor code steps require the matching challenge fingerprint; both sweeps remove its challenge, fence, OTP, attempt counter and trusted-device rows. Other session creation requires a live parent row before AND after insertion (including 2FA enable/disable and enrolment). Unknown paths and missing contexts are refused. Admin impersonation and direct password-setting remain forbidden by the existing admin role; the fence grants no authority. Session refresh updates an existing row and cannot resurrect a deleted row. Both reset sweeps delete ALL owned sessions. A change with sign-out-other-devices keeps only its returned token and revokes standing MCP credentials; a change without it retains other sessions by the user's choice.

Password writes serialize under `password-write:<userId>` for the whole POST `/api/auth/change-password` or `/reset-password` handler (`password-auth-handler.ts`, shared by the server and any operational caller). Admin password-setting is not mounted in this app because its admin role forbids it; server-only Better Auth `setPassword` calls are also refused without the lock. A change waiting behind a reset rechecks its live session inside the lock and writes nothing if it vanished; a reset behind a change runs last. Password-bearing account creates/updates require the lock, except a new user's sign-up or server-granted admin invite. After-hooks probe that the lock transaction is still open and its held flag has not lapsed. A delayed write that fails confirmation is quarantined: an unusable peppered credential is committed first, then every session, 2FA challenge and standing MCP credential is revoked, and the request fails with `PASSWORD_WRITE_UNCONFIRMED` (409) and no new cookie. Recover with a fresh Forgot password link. Writers wait at most 10 seconds, then answer `PASSWORD_WRITE_BUSY` (503); the lock's 30-second transaction stops counting as held after 25 seconds.

Lock order: **password-write → user credential/revocation → set-password-link**. `oauth-revocation.ts` is the existing credential lock; MCP token creation/regeneration, consent/grant creation and revocation all share it, with a live-session recheck for session-authorized mints. OAuth refresh reuses an existing grant under this lock; reset tombstones that generation permanently. Even a refresh that has passed its claims check before reset and finishes serializing afterward cannot use its signed token at MCP or refresh that generation again, because both paths re-read the tombstone. The one DB setup lock is `lockCredentialSetup` in `password-reset-links.ts`; minting and completed-reset link cleanup use it. The existing process-local password-link delivery gate refuses duplicate sends but holds no DB connection and is never acquired by reset. No later DB lock waits for an earlier one. `lock-slots.ts` accounts for all pooled advisory-lock holders, including startup pepper conversion/recovery. Password writes reserve their own and one nested slot together, leaving a connection free for Better Auth's work: `DATABASE_POOL_MAX` must be at least 3. No migration is required. SMTP is outside setup transactions; global adapter transactions remain off because sign-up's locale query uses global Prisma and mail delivery can take 40 seconds, beyond Prisma's default 5-second transaction timeout. Only reset requests use the selective adapter transaction; request-aware transaction metadata persists after a lock lapse so rolled-back writes cannot run queued account after-hooks. Verification updates accept only exact scalar, case-sensitive user ID or immutable email selectors and serialize password-write, the existing two-key credential lock, then the single setup lock on one client. The reserved nested slot is used for reset; activation uses one transaction, without an inner credential transaction or an additional lock namespace.

The enabled JWT/MCP/OAuth-provider/CIMD plugins contain no browser `createSession` calls. No device-authorization, API-key, magic-link or other session-minting plugin is enabled. The path list must be audited again when plugins or Better Auth change.

Remaining limits: signed cookie-cache reads may answer for up to 60 seconds; credential mints recheck the authoritative session under the issuance lock. Reset announces teardown after the final session sweep, closing streams/MCP exchanges admitted while that sweep was in flight; quarantine also announces after its sweep. Teardown still runs if the sweep fails. A raced 2FA disable may change the flag but receives no session. If the password write fails before commit, existing sessions stay deleted, but the old password still works and an in-flight sign-in may complete. The selective reset transaction rolls back token/proof changes, so retry the same link; no post-sweep runs. Post-commit cleanup failures cannot roll back a committed password, are logged as SECURITY and propagate; a credential minted before the new hash commits requires manual revocation if all post-sweep retries fail.

Saved SSH private keys are encrypted using `COCKPIT_CONTEXT_ENCRYPTION_KEYS` and never returned. One-time snapshot keys are request-local unless explicitly saved. Verify SSH fingerprints independently. Archiving an account revokes its sessions and MCP credentials and stops all of its runs (main and overview summary, queued or running); unarchiving does not restore them. `users.passwordLink` is the one admin path to a user's password, and only for non-admin password accounts: with SMTP the link goes only to the user's mailbox (a failed send revokes it), but without SMTP the admin holds a link that would set the user's password, so every link writes an `[audit]` log line and the privacy notice says so. MCP credentials do not require an interactive second factor per request.

Anonymous auth endpoints do not reveal whether an address has an account. With SMTP, sign-up answers byte-identically (status, headers, body `{"token":null,"user":null}`) for a free and a registered address, verified or not: an after-hook in `packages/auth/src/signup-response.ts` replaces Better-Auth's success body (whose synthetic duplicate user lacked the admin plugin's `role`), and while sign-up is closed a 200 stands only for a real first-admin bootstrap. Open or closed is decided once per request, at its start, for both the account creation and the response, so a sign-up already admitted when an admin closes sign-up still completes; `packages/auth/src/signup-response.test.ts` pins this on the production auth handler. When nobody may self-register, `signupAvailabilityGate` refuses every sign-up with the same 403 before Better-Auth runs. While no account exists, the first-admin bootstrap is the only creation the user-create hook admits, whatever the sign-up setting: a wrong token, an unlisted address and SSO all get the same refusal, so nothing reveals `ADMIN_EMAILS` membership and a typo cannot create a plain first account. Resend verification, password-reset request and wrong-password sign-in are uniform in Better-Auth. Intended differences: the right password on an unverified account answers 403 `EMAIL_NOT_VERIFIED` and re-sends the link; a sign-up of a free address creates the account, so its own later sign-in, its extra time (rows and the verification mail) or a concurrent duplicate can show it *was* free; and open sign-up without SMTP signs a new address in while a registered one gets 422 "already exists" (unverified open sign-up, warned about at boot; keep sign-up closed without SMTP).

Dependency content and model output are untrusted. Read tools are confined; required Landlock failure disables language-server tools. Runs have time, iteration, concurrency and rate budgets. Summary runs share the global cap but are exempt from the user main-run cap. See [product limits](./product.md#limits) and [deployment](./deploy.md).
