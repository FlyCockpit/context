# UI

Layout rules for the web app that the code alone does not make obvious. The general rules (one scroller, overlays, touch targets, i18n) live in [AGENTS.md](../AGENTS.md); this file records measured values.

## Edge lines

This app follows the template's edge lines (FlyCockpit/template, `patterns/design-system.md` § Edge lines). This section lists only where this app's shell differs from them or adds containers the template does not have. Change a value only with the maintainers' approval, and record the new value here.

Terms are the template's. The **text line** is where labels, headings and bare icons start. The **box line** is where filled, bordered or shadowed controls start. The **trailing line** is where the last item in a row ends. An item is within tolerance when its ink is within 1px of its line. Values hold at 390px and 1440px unless a row says otherwise.

The template's two rules apply here too. Boxes share the text line inside pages, cards, sheets and forms. A miss is fixed in the container (its padding, `inset`, `px-*` on a track, or the shared close-button placement), never with a one-off margin on one item.

So do the template's five rules from the apps' passes:

- **An edge text item puts its label on the box's edge.** When a text link or button is the first or last item on a line and its box is wider than its label (a 44px minimum box around a short label), start-align the label (`justify-start`) for a leading item, end-align it for a trailing one. Centring is for items in centred bars, such as BottomNav, and for icon buttons.
- **Table text sits on its container's text line.** The first and last cells drop their outer padding (or take the container's inset, e.g. `first:pl-0 last:pr-0`). Inner cell padding separates columns; it must not indent the first column from the heading above the table.
- **Overriding a Button's padding: override every breakpoint.** tailwind-merge treats `px-*` and `md:px-*` as separate groups, so a `className="px-2"` leaves a responsive size padding in force at that breakpoint. Write `px-2 md:px-2` whenever the size carries one.
- **A control flush with a clipping edge draws its focus ring inside its box** (`focus-visible:ring-inset focus-visible:ring-offset-0`). Button's default ring is drawn 2px outside the box after a 2px offset, and the viewport or an `overflow-*-hidden` ancestor cuts it off.
- **Frame bands keep the frame line.** Bands above the page (`TwoFactorNudge`, `AdminSetupBanner`) and the header sit 16px inside the frame. A band's content stops at the widest page column (§ Viewport scale), so on a screen wider than that column it lines up with the widest page, not with the frame; it is never re-aligned to a narrower page container below it (see the two-factor nudge row). `TwoFactorNudge` is inside the page column beside the sidebar; `AdminSetupBanner` spans the whole window above it, so its column centres in the window (half a sidebar from the page column on wide screens; message and action still sit together). The header keeps the frame line at every width.

## Shell rules

This app follows the template's shell rules (FlyCockpit/template, `patterns/design-system.md` § Shell rules), adapted to its shells. Four rules every page meets, in both themes and at every width. `pnpm policy:checks` enforces what a static check can (gate 4 of `scripts/check-agent-rules.ts`: rules G8 and G9 in `scripts/check-web-conventions.ts`; G10 is § Viewport scale), `apps/web/src/components/public-shell.test.tsx` and `scripts/lib/theme-contrast.test.ts` pin the markup and the tokens, and `pnpm check:layout --url <web dev server>` measures the geometry in a browser (`scripts/check-layout.ts`; local only, it needs agent-browser and the dev stack; add `--login <admin email>` with `CHECK_LAYOUT_PASSWORD`, and `CHECK_LAYOUT_TOTP` for an account with a second factor, for the signed-in pages).

1. **The footer sits at the bottom of a short page.** The public shell (`apps/web/src/components/public-shell.tsx`, used by the `_public` layout and the 404) owns the one public footer (`components/public-footer.tsx`, the privacy notice link). Inside `<main>`, the content is one `flex min-h-full flex-col` column: the routed page grows (`flex-1`) and the footer comes last. On a short page the footer's bottom is the scroller's bottom; on a long page it follows the content. Its bottom padding clears the safe area (the iOS home indicator). No `position: fixed` footer, no `min-h-svh` layout, no second scroller, and no site `<footer>` in a route file: footer content goes into `PublicFooter`; a `<footer>` that belongs to an `<article>`, `<section>` or similar stays inside that element. A page that should fill the remaining height (a centred empty state) uses `flex-1`. The app shell (`_app`) has no footer: phones get the BottomNav.
2. **Full-bleed dividers span the viewport.** The header's `<hr>`, the footer's `border-t`, sticky sub-navs (the admin section nav) and full-width bands (the 2FA nudge) reach from the start of their column (0, or AppFrame's content column after the signed-in sidebar) to the viewport's right edge at every width; on a page that scrolls, rules inside `<main>` meet its visible scrollbar, which sits at that edge, as on any scrolling page. That is why neither `<main>` reserves a scrollbar gutter: with classic scrollbars (Windows, Linux) a stable gutter is an empty 15px strip that every rule inside the scroller stops short of, even when nothing scrolls. The cost is that centred content moves by half a scrollbar when a page grows past the viewport on those platforms; overlays don't cause it, because Base UI locks the document, not `<main>`. Nested panes (the conversation transcript) may still reserve a gutter.
3. **No surface ignores the theme.** The theme is the stored choice (`cockpit-context-theme`), else the OS, applied as the `.dark` class before first paint (`packages/config/src/theme-init.ts`). Every surface (toasts, banners, popovers, menus) uses the tokens in `packages/ui/src/styles/globals.css` and `dark:` variants, never a `prefers-color-scheme` query or a literal colour (`url(#id)` is a reference, not a colour); a new colour becomes a token there. A deliberate fixed colour (a QR code that must stay dark on white to scan) carries `theme-exempt: <reason>` in a comment on the line above it, on its line, or inside the flagged className/style value; G9 skips that finding and nothing else. Toasts are a popover surface: `globals.css` fills sileo's pill with `--popover`, writes the title and description in `--popover-foreground` and maps sileo's state colours to `--state-*`, `--destructive` and `--primary-text`, and the Toaster gets no `theme` prop (sileo's themes invert the page). Text and state colours reach 4.5:1 on the surface they sit on in both themes.
4. **Every route renders inside a shell, the 404 included.** An unknown URL matches no layout, so `$lang`'s `notFoundComponent` (`PublicNotFoundPage`) wraps the not-found state in the public shell: header with language and theme controls, footer, scroller. The router's `defaultNotFoundComponent` stays the state alone, and Settings and Access set their own nested one, so an unknown sub-path there keeps the app shell. A `notFound()` thrown by a route without its own `notFoundComponent` (the admin gate) lands on the same public 404, so a hidden admin page looks exactly like an unknown URL.

## Viewport scale

The app grows with the screen above 1920 CSS px, so a 4K monitor at 100 % OS scaling shows the same layout as a 1080p one instead of a small island in the middle. Phones, laptops and 1080p screens are unchanged. Same rules as the template (`patterns/design-system.md` § Viewport scale).

1. **One root rule scales everything.** `html` in `packages/ui/src/styles/globals.css` sets `font-size: clamp(100%, calc(100% + (max(100vw, 100vh) - 1920px) / 240), 150%)`. The root is the browser default (100 %, so a user's own default font size is respected) up to a 1920 CSS px long side, then grows 1px per 240px, capped at 150 % of that default. With the usual 16px default that is 24px at 3840, and it stays there; a larger default gets the same +1px per 240px on top (20px → 28px at 3840, capped at 30px). The long side makes a portrait 2160×3840 screen scale like a landscape 3840×2160 one; 4K at 200 % OS scaling is 1920 CSS px, so it is unchanged. Media queries use the browser default, so breakpoints don't move, and browser zoom still enlarges. `apps/web/src/lib/viewport-scale.test.ts` pins the rule.
2. **Sizes are rem, not px.** Type, control heights, padding, page widths, dialogs, sheets, cards and images use Tailwind's rem scale, so they follow rule 1. A px size does not scale: next to rem siblings it ends up too small at 4K (a px switch track around a rem thumb overflows). px stays for hairlines and borders, shadows, radius offsets and touch-target floors (`min-h-[44px]` is a minimum, not a size).
3. **Text is at least 12px** (`text-xs`, 0.75rem) at every width, labels and badges included; 18px at 3840. A BottomNav label that doesn't fit truncates (the tab's accessible name stays whole). Rule G10 in `scripts/check-web-conventions.ts` (`pnpm policy:checks`) rejects, in any class list in web source, a px font size (`text-[13px]`), a rem size below 0.75, an em size below 1 (it drops under 12px inside 12px text) and any other size expression without a 0.75rem floor; `text-[length:max(0.9em,0.75rem)]` (Markdown's inline code) passes.
4. **Pages use the width tiers.** `PageShell`'s `narrow`, `default` and `wide` (`apps/web/src/components/page-shell.tsx`) are rem, so they scale with rule 1. Dense tables scroll inside `WideContent`, never the page.
5. **Full-bleed bands keep their content in the page column.** The background and border span the scroller; the content goes in `PAGE_COLUMN_CLASS` (`page-shell.tsx`, the `wide` tier), so the message and its action sit together instead of 3000px apart at 4K.
6. **Long copy gets `max-w-prose`** (45-75 characters per line): the privacy notice, descriptions, help text, policy explanations. `PageHeader`'s description carries it already.
7. **The header stays full width**; its row scales with rule 1.

## Form surfaces

This app follows the template's form-surface rule (FlyCockpit/template, `patterns/design-system.md` § Form surfaces). The shared pieces live in `apps/web/src/components/form-surface.tsx` until the template's components are ported.

- **Dialog**: confirmations and short forms only, about 6 controls or fewer, fitting **without inner scrolling** at 1280×800 and 390×844 (the dialog-fits check). Create token, Invite user, Ask, Add git host, Generate/Import key, Reject proposal and every type-to-confirm delete are dialogs.
- **Wide form sheet** (`FormSheetContent`): anything longer, and long read-only details. Full screen on phones, `max-w-xl` from `sm:`, `max-w-3xl` from `lg:` with two field columns. The header stays at the top, the action bar (`FORM_SHEET_FOOTER_CLASS`, primary action last) stays at the bottom, and only the fields between them scroll (`FORM_SHEET_BODY_CLASS`). Add package, Approve proposal, Edit package, Checkout overview and Edit overview are sheets.
- **Quick path first**: the few fields most people decide (Add package: ecosystem, name with the registry lookup, git URL; the SSH key only for SSH URLs). Fields with safe defaults go in a collapsed `AdvancedSection` whose summary line shows the current values ("Shown as … · Starts in the repository root · Tags: usual patterns · No version: default branch · No notes"), so nothing is hidden. Edit forms use the same split as their create form.
- **Errors** appear inline under the field; a failed submit focuses the first invalid control and opens the Advanced section that holds it (`focusFirstInvalid`).
- **One thing at a time** for results: the new-token view shows the token and one client's setup (Claude Code, Codex or other clients), not every snippet stacked.

The field-by-field triage behind these choices is recorded in the forms-ctx run notes; a new create/edit surface states its essential fields and its Advanced defaults in its PR.

## Sign-up modes

The landing page, sign-in and `/signup` read one value, `signupMode(appConfig)` (`apps/web/src/lib/signup-mode.ts`), so they tell the same story: `open` (sign-up on, only once an account exists), `bootstrap` (no account yet; the `ADMIN_EMAILS` address with the boot-log token creates the administrator), `closed` (invite-only) and `sso` (`FORCE_SSO`).

- **Landing** (`LandingActions`, from `landingEntry`): bootstrap leads with "Set up this server", open with "Create account", Sign in follows as an outline button; closed shows Sign in and the line "This server is invite-only. Ask an administrator for an invitation."; SSO-only shows Sign in alone. Unlike the template, whose bootstrap flag stays true after the admin exists (so it keeps Sign in primary there), this app's bootstrap flag turns off with the first account, so "Set up this server" stays the main action. The mode comes from a client query: the SSR (and cached) HTML shows the neutral Sign in.
- **Sign-in**: under the form, the sign-up link while open, the invite-only line while closed, nothing under SSO. While the bootstrap is open the page is the `AdminSetupCard`.
- **/signup**: closed renders the "Sign-up is closed" card (no redirect), SSO redirects to sign-in, bootstrap asks for the token.
- **Password rule up front.** Every new-password field (sign-up, reset/invite/setup link, change password) shows "At least 12 characters." as its description and validates with `newPasswordSchema()` (`apps/web/src/lib/password-policy.ts`), built from the same `@cockpit-context/auth/password-policy` constants Better-Auth enforces. A confirm field checks only "required" and the match, so the rule is reported once.
- **A way back.** Every step of a multi-step auth flow has Cancel: the sign-in 2FA challenge returns to the form with nothing kept; the 2FA enrollment (Settings → Security and the forced-setup screen) returns to its start from the password, backup-code and verify steps and forgets the unconfirmed secret. The passwordless-enrollment sentence shows only when SSO is enabled.

## Server errors on a field

A server answer about one field goes under that field, with the same `aria-invalid`, `aria-describedby` and `role="alert"` wiring as a validation error: `setServerFieldError(form, field, message)` (`apps/web/src/lib/form-server-error.ts`) writes the field's `onSubmit` error slot (TanStack Form derives `meta.errors` from `errorMap`, so writing `meta.errors` does not stick). It clears on the next edit of that field, and until then the form cannot resend the same values. Inputs kept in local state use `PlainField` / `OneTimeCodeField` (`components/auth/plain-field.tsx`). Focus returns to the field with its text selected.

- Sign-in: only a credential rejection (`isCredentialRejection`, `utils/friendly-error.ts`: the `INVALID_EMAIL_OR_PASSWORD` code, not any 401, since Better-Auth also answers 401 `FAILED_TO_CREATE_SESSION` after correct credentials) goes under the password field, never saying which of the two was wrong, and editing the email clears it too (`clearServerFieldError`), so fixing only the email makes the form submittable; "email not verified" is an inline `role="alert"` notice under the email field with a "Send a new link" link (not a field error, since the same credentials work after the inbox link); a rate limit, server or network failure stays a toast with `friendly()`'s own copy, never "doesn't match", and a request that throws (server unreachable, offline) is caught and shown the same way. The MCP sign-in page follows the same rules.
- 2FA verify (sign-in challenge, enrollment in settings and the forced-setup takeover, MCP sign-in): only a code rejection (`isCodeRejection`: `INVALID_CODE`, `INVALID_BACKUP_CODE`, `OTP_HAS_EXPIRED`) says "invalid code", under the field where there is one; a rate limit, lockout, expired 2FA session, server failure or thrown network error is a `friendly()` toast with its own copy (no "invalid code" fallback, so a 503 reads as a server failure) and the code is kept so it can be sent again.
- A wrong 2FA code (sign-in challenge, enrollment verify, MCP sign-in), a wrong password when starting enrollment, and a wrong current password on change password are inline. Every 2FA step, the MCP one included, has a Cancel back to the credential form that clears the challenge. An address already registered (`isAccountExistsRejection`: Better-Auth's 422 `USER_ALREADY_EXISTS_USE_ANOTHER_EMAIL`, sent only without SMTP) goes under the sign-up email field; with SMTP a registered address gets the same neutral success as a free one (`packages/auth/src/signup-response.ts`), so there is nothing to show and no enumeration oracle. A sign-up request that throws is a `friendly()` toast, and so is a failed "email me a code" request on the 2FA challenge.

## Offline and network failures

- **Band.** `OfflineBand` (`components/offline-band.tsx`) sits in each shell's top row, after the header (and the admin setup banner) and outside `<main>`, so it takes its own height and never covers the page, the BottomNav or a sheet. It says "You're offline. Changes you make won't be saved until you reconnect." while `navigator.onLine` is false and "Back online." for 4 s after a real reconnect. Its `role="status"` live region is always mounted (empty while online), its colours are theme tokens (`bg-muted`, `text-state-warning` / `text-state-success` icons), and it only fades in under `motion-safe`.
- **Classifier.** `networkFailureKind(error)` (`lib/network-failure.ts`) is `offline` (no network and no HTTP status), `unreachable` (online, the browser's fetch `TypeError`) or `null`. `friendly()` maps the first two to "You're offline. Check your connection and try again." and "Couldn't reach the server…" before any fallback, so every toast and inline error says what to do. The global query-error toast skips `offline` failures.
- **Mutations fail fast offline.** `installOfflineMutationPolicy` (`lib/offline-mutations.ts`, installed in `router.tsx`) makes `networkMode: "always"` the default: offline, a mutation fails at once with the offline message, its button settles and Cancel works again (Add package, Look up, every dialog). `meta: { offline: "queue" }` opts a replay-safe write into TanStack's paused queue, with one "will be sent when you reconnect" notice and a "sent" notice; an explicit `networkMode` wins. No mutation in this app opts in: none relied on the paused queue, which used to hang silently (CTX-04). Never queue a write that is not safe to replay (creates, deletes, anything spending money or tokens).
- **Queries and route errors.** A first load that TanStack paused for the network renders `QueryBoundary`'s offline InlineRetry ("This will load when you reconnect.") instead of a skeleton forever; loaded data stays on screen. The router's `ErrorState` says "You're offline" and reloads the failed matches on reconnect by itself, or "Couldn't reach the server" for an online fetch failure, without a Reload button (reloading offline lands on the browser's offline page). Stale-build recovery (`lib/stale-build-recovery.ts`) never reloads while offline, and offline it also marks TanStack's own once-per-error slot (`sessionStorage["tanstack_router_reload:" + message]`, `suppressRouterReload`) so `lazyRouteComponent` does not reload on an uncached route's failed import; online, that TanStack reload is left as it was.

## Copyable values

`CopyField` (one line) and `CodeSnippet` (a block) share one code size, `font-mono text-xs leading-5`. The copy button sits in its own 44px column beside the value, never over it, so scrolled text is never hidden under it. A long value scrolls inside its box and fades out at the edge that has more to scroll (`scroll-fade-x`, set by `useScrollEdges` in `packages/ui/src/hooks/use-scroll-edges.ts`). `CodeSnippet`'s `wrap` wraps long lines instead (logs, tool output); commands and config keep one line per line.

## Toasts

Each toast gets its own id (`packages/ui/src/components/sileo.tsx`), so two toasts stack instead of the second replacing the first (sileo's default id is shared). The pill is one line, capped at sileo's 350px width with an ellipsised title (`globals.css`); a message over 40 characters is repeated in the description, which sileo expands under the pill. The action button's text reaches 4.5:1 on its tint (`scripts/lib/theme-contrast.test.ts`).

## Settings that are on or off

A setting that is on or off shows a `Switch` named by the setting's title, with visible "On" / "Off" text beside it in a 44px label, never only a button verb such as a red "Disable" (`components/admin/security-policy-card.tsx`). A prerequisite (set up your own 2FA before requiring it for others) is not an error: it is an info note (`role="note"`, `bg-state-info-bg`, Info icon in `text-state-info`) with a real link button to the place that fixes it, and the switch it blocks is disabled with the reason beside it (`aria-describedby`). Turning a policy off is never blocked.

## Smaller rules

- **Field outlines** (`--input`: inputs, textareas, selects, checkboxes, the switch track) reach 3:1 on background, card, popover and muted in both themes (WCAG 1.4.11); `--border` stays a light decorative line.
- **Menus** draw on an opaque `bg-popover` (no translucency or blur), and a menu that picks the current choice (the theme menu) uses radio items, so the current value is checked.
- **Selector rows** (`SelectorRow`: the admin strip, section tabs, segmented controls) fade out at an edge with more tabs past it, re-measured on scroll and resize, and scroll a focused tab clear of the fade (instantly under reduced motion).
